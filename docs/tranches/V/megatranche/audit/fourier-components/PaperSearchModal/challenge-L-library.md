### L-2 · BLOCKER · Two `PaperSearchModal` instances mount simultaneously below 1024 px, off one shared state — the teleported subtree is duplicated in `<body>`

**Falsifier.**

2. *`lg:hidden` on the floating TOC prevents reaching the expand control on desktop* → **TRUE, and that is the bound**: at ≥1024 px `.floating-toc` is `display:none`, the search affordance is unclickable, `searchActive` stays `false`, and exactly one modal exists. ### L-5 · MAJOR · `SearchResult.matches` is computed, shipped, and never read; the highlighter re-runs the full fuzzy match per row per render
`paperSearchIndex.ts:48-52` declares `matches: number[]` ("Matched character indices into the display label, for highlighting"), `:185` populates it, `:234` ships it on every result. **No consumer reads it**: `grep -rn "\.matches" web/src` → only the two internal producers (`:153`, `:185`), the `{...entry, matches: m.matches}` write (`:234`), `searchHelpers.ts:45` reading *its own* freshly-computed `m.matches`, and three unrelated `matchMedia().matches` hits. The field is **dead payload**.
Instead, `PaperSearchModal.vue:100` calls `highlightFuzzy(resultLabel(r), search.query.value)` **inline in the `v-for` body**, which re-tokenises the query and re-runs `fuzzyMatch` per token per row (`searchHelpers.ts:38-47`), then escapes **one character at a time** through three regex passes each (`:64` → `:73`). Because `:88` `:class="{ 'is-selected': i === search.selectedIndex.value }"` sits inside the same loop, **any** `selectedIndex` write re-renders the whole block — and `:90` writes it on **`@mouseenter` of every row**. Moving the pointer across the list therefore re-runs, per row crossed, up to 30 × (tokens × |label|) fuzzy scans plus ~200 × 3 regex executions of `escapeHtml`. There is no `computed`, no `v-memo`, no memo cache.
**Why the dead field exists:** `paperSearchIndex.ts:185` `bestMatches = text === entry._lc.label ? m.matches : []` yields indices into the **lower-cased** field, while `resultLabel(r)` (`searchHelpers.ts:24-28`) returns the **original-case** label — or a `rawTex`/`plainText` slice for entries with no label. The indices genuinely do not align, so the re-run is a *correct workaround for a broken contract*; the defect is that the broken half was never deleted.
**Falsifier:** *Vue hoists the call* → impossible; the expression closes over the loop variable `r` and the reactive `search.query.value`. *The list is short* → `usePaperSearch.ts:36` caps at **30**, and labels run to 200–300 chars (`paperSearchIndex.ts:319,328,339,354`). `UNPROVEN-NEEDS-LIVE` for the millisecond cost; the re-evaluation and the deadness are static facts.

### L-6 · MAJOR · Result identity is not unique — the index key hides it, and `selectResult` navigates to the wrong place
`selectResult` (`PaperSearchModal.vue:89` → `usePaperSearch.ts:43-46`) calls `navigateTo(r.id)`. But `buildSearchIndex` assigns **`id: sectionId`** as a fallback or outright: equations `:302` (`block.id ?? block.anchorId ?? sectionId`), theorems `:316` (`thm.label ?? sectionId`), figures `:325` (`fig.label ?? sectionId`), **code blocks `:334` (always `sectionId`)**, **proofs `:350` (always `sectionId`)**. Two proofs in one section produce two entries with **identical `id` and identical `type`** — so `${r.id}-${r.type}` collides, and the `:key` at `:85` only survives by splicing in the array index `i`. Including `i` in a `v-for` key defeats keyed reconciliation entirely: any reorder (and the list reorders on every keystroke, `usePaperSearch.ts:35-37`) forces destroy/recreate from the first changed position rather than a move.
Downstream: clicking the *second* proof in a section navigates to the section heading, indistinguishable from clicking the first. Same for code blocks, and for any unlabelled theorem/figure/equation.
**Falsifier:** *`id` is always unique* → refuted by `:334` and `:350`, which take no fallback path at all. *The index key is harmless because keys need only be unique* → uniqueness is satisfied, **stability is not**; that is the property `:key` exists to provide. *`navigateTo` disambiguates* → `useScrollNavigation` receives a bare id string (`PaperView.vue:99-109`); it has nothing else to go on.

### L-7 · MAJOR · A composable's return bag is prop-drilled through four component boundaries; the declared emit contract is dead and replaced by direct mutation of parent state

### L-8 · MAJOR · The prefix-narrowing search cache is lossy — a longer query can never recover a row the shorter query truncated away

Confirmed.** *`maxResults` is large enough to be safe* → `usePaperSearch.ts:36` passes **30** against an index that walks every section, theorem, equation, figure, code block and proof in the paper (`:369-400`). *This is a deliberate speed/recall trade* → nothing in the file says so; `:219` comments *"narrow from those"*, implying the author believed the prefix set was a **superset**, which it is not.
