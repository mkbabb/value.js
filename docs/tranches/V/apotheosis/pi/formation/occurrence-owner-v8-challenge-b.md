## Blocking findings

### B1. The closed disposition/no-throw claim fails on exact reference inputs

`scanReferenceCandidates()` classifies a bare CSSWG host URL as an included
`spec_url`. `parseReference()` then derives the name from the first pathname
segment and calls `name.toLowerCase()` without proving a segment exists
(`discover.mjs:347-356`). Both of these exact inputs throw:

```text
https://drafts.csswg.org/
<a href="https://drafts.csswg.org/">root</a>
```

Observed result under the frozen Node v26.0.0 runtime:

```text
TypeError: Cannot read properties of undefined (reading 'toLowerCase')
at discover.mjs:356:46
```

The active-href variant is especially material: the lexical pass positively
classifies the parsed `href`, then the formation aborts instead of returning a
RED disposition. The 29 counterfixtures contain ordinary draft URLs but not
the zero-segment boundary.

Candidate completeness also fails under malformed nesting. For the exact
UTF-8 text below (one leading backslash), the scanner finds the closing `=]`
belonging to the inner shorthand while processing the escaped outer opener,
marks one span at byte offsets `[1,18)` excluded, jumps to offset 18, emits zero
references, and creates no disposition for the unescaped inner opener at byte
9:

```text
\[=outer [=inner=]
```

That contradicts the receipt's assertion that every carrier/reference
candidate receives one stable included or reviewed-excluded row. The universe
of 160,605 candidates is the output of this scanner, not an independently
closed candidate denominator.

### B2. The claimed single parsed lexical/structural model still admits false structure and false raw-pre references

Processed `code`/`samp` is deliberately eligible for Bikeshed shorthand, but
that does not make Markdown structure inside it active. `headingFromLine()`
uses `activeStructureAt()`, which includes `BIKESHED_CODE`. This exact input:

```html
<code>
# Parse Algorithm
</code>
<dfn>after</dfn>
```

produces a `BIKESHED_ATX` heading titled `Parse Algorithm` and an
`algorithm_section_candidate` spanning lines 2–4. The literal code content has
therefore changed downstream section ancestry and operation discovery.

The raw-pre classifier is also a narrow spelling list, not the advertised
general boundary. It recognizes a valued `highlight` attribute and `lang-*`
classes, but neither a boolean `highlight` attribute nor a
`language-javascript` class. Each of these exact inputs emits `'running'` as an
included `css_shorthand_single` in `BIKESHED_TEXT`:

```html
<pre highlight>
'running'
</pre>
```

```html
<pre class="language-javascript">
'running'
</pre>
```

The authenticated `lang-javascript` witnesses remain fixed, but they do not
prove the claimed raw-pre class. These counterexamples also show why exact
corpus witness counts cannot substitute for a closed lexical contract.

### B3. Reference target joins bypass parsed attributes and can be fabricated by unrelated quoted prose

The top-level tag, container, and algorithm paths consume parsed attribute
tokens, but `definitionMetadata()` reverts to `shared.mjs`'s raw regular-
expression `attribute()` helper for `data-dfn-for`, `dfn-for`, `for`,
`data-dfn-type`, `dfn-type`, `data-lt`, and `lt`
(`discover.mjs:442-475`; `shared.mjs:71-75`). That regex can match attribute-like
text inside an unrelated quoted value.

Using one carrier for the exact `<dfn>term</dfn>` interval, this input:

```html
<div title="prefix data-dfn-for='Ghost' suffix"><dfn>term</dfn></div>
[=Ghost/term=]
[=term=]
```

produces the wrong cross-shard relation: `[=Ghost/term=]` targets the carrier,
while `[=term=]` is unresolved. `Ghost` came solely from `title` prose. This is
not merely an owner-review ambiguity; it is a mechanically fabricated target
edge in the RED reference graph.

The relational verifier checks that target indexes are in range, but it does
not recompute target semantics (`verify.mjs:250-265`). The mutation named
`D-reference-stale-carrier-target-foreign-key` is rejected by the blanket
expected-byte oracle installed at `mutations.mjs:33,51-54`, before that test can
prove semantic target equivalence. The current exact bundle is internally
stable, but a generator that deterministically produces the wrong target can
regenerate and verify the same wrong bytes.

### B4. The operation denominator is a keyword/tag heuristic with concrete misses and false positives

Operation discovery admits headings only when title/anchor text matches the
closed `OPERATION_WORDS` regular expression, or when an element carries an
algorithm marker; it admits every `<dt>` independently of operation semantics
(`discover.mjs:35,240-290`). Exact probes show both directions of error:

```text
# Procedure
1. Convert the input.
```

and

```text
# Convert a color
1. Return the result.
```

each produce zero operation candidates, whereas changing only the heading to
`# Parse` produces two. Conversely:

```html
<dl><dt>Color</dt><dd>A perceptual quality.</dd></dl>
```

produces a `definition_term_and_body_candidate` despite containing no
operation. An inclusive RED queue may retain false positives, but it may not
claim full occurrence closure while normative procedures can disappear based
only on heading vocabulary. Ten inherited required slices and 311 marked
openings are regression anchors, not a bidirectional normative occurrence
matrix.

### B5. Semantic regeneration and the 33 mutations are not independent enough to establish the advertised relations

`verify.mjs` imports the same `discoverAll()` and `assembleTables()` functions
as the generator. In the actual generation path, `core.mjs:185-186` goes
further: it passes each just-produced semantic shard byte string back as
`expectedSemanticBytesByTable`. Consequently, the check at
`verify.mjs:80-85` proves equality with the generator's own bytes, not an
independent reconstruction from a separately implemented occurrence model.

The mutation suite repeats that pattern. It stores the original bytes for all
eight semantic tables and treats any thrown exception as success without
asserting the rejecting invariant. Therefore most named semantic mutations
are guaranteed to reject at whole-table byte equality even if their intended
schema or cross-shard relation is absent. This is useful tamper detection, but
it does not establish generator correctness or mutation coverage.

No frozen mutation covers the throwing draft-root URL, nested escaped opener,
processed-code heading, alternate raw-pre marker, quoted fake dfn attribute,
unmarked procedure, duplicate candidate-to-disposition cardinality, truncated
ID collision handling, launcher substitution, import restore race,
publication fault points, or adversarial work growth. `33/33` must not be read
as broad mutation adequacy.

### B6. The attestation trust root does not authenticate the launcher before it executes

`launch.mjs` is already executing when it reads its own bytes. It compares the
nine imported modules and two schemas to constants, but it has no frozen
expected identity for itself; it simply records its current bytes at
`launch.mjs:75-80`. The manifest schema likewise accepts any well-formed
launcher identity. A changed launcher controls the module constants, runtime
constants, validator constants, and attestation object. An external exact
subject hash lets this challenge identify today's launcher, but the replay
command itself does not verify that trust root before execution.

The declared module-set digest contains nine modules and excludes the
launcher. The receipt's ten-row “Frozen tool identities” table should not be
described as one pre-execution module set.

The disclosed path-import TOCTOU is real: a module can be replaced after the
disk precheck, evaluated, and restored before `assertPostImportAttestation()`;
the imported code remains live. The disclosure preserves honesty about that
known gap, but two additional facts remain: Ajv's package tree has no
post-import identity check, and `--fixture-only` returns at `core.mjs:163-165`
before the post-import module/schema check at line 169. Thus the fixture RSS
assay is not evidence for the advertised post-import boundary.

### B7. The memory ceiling is a sampled gate, not a sealed peak/work-limit proof

The executable samples `process.memoryUsage().rss` only at selected milestones.
It cannot see a higher RSS between samples. The receipt's three maximum-RSS
numbers appear only in prose: there is no content-addressed raw resource
record, exact `/usr/bin/time` invocation/result, source-root identity at the
assay boundary, output location, environment, or failure-retention record.
The highest stated value, 917,258,240 bytes, leaves only 26,460,160 bytes below
the 943,718,400-byte ceiling.

A fresh fixture-only run did pass and `/usr/bin/time -l` observed 71,974,912
bytes maximum RSS (the receipt states 71,680,000). The small variance is not a
semantic failure; it demonstrates why raw run evidence and repeat methodology
must be sealed rather than transcribed.

There is also no input work limit. An unterminated quoted tag makes
`parseTagAt()` scan to EOF for every later `<`. Under the frozen Node runtime
and `--max-old-space-size=650`, the exact family
`'<a "' + '<a '.repeat(n)` produced:

| UTF-8 bytes | elapsed milliseconds |
|---:|---:|
| 24,004 | 134.494 |
| 48,004 | 515.270 |
| 96,004 | 1,696.033 |

Timing is necessarily noisy, but the implementation and near-quadratic growth
agree: doubling this malformed input causes each opener to rescan most of the
remaining source. A fixed-corpus peak-RSS pass does not satisfy adversarial
work-bound methodology.

1. a recovery-defined, work-bounded lexical/reference pass that gives every

   semantics;

   rather than keyword/tag coverage;
