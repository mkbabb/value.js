### Observed outside the batch (for the orchestrator; no verdict row)
**On this served model, every browser write that carries `Idempotency-Key` fails the CORS preflight.** `api/src/platform/http/cors.ts:34` allows only `Content-Type, X-Session-Token, Authorization`, so the client's `Idempotency-Key` (`demo/platform/transport/client.ts:115/:148`) is rejected. `If-Match` would be rejected for the same reason.
- **Witness:** cell `cors` in `E/run-b12-cors+inj+owned.json`:
  - The POST to `/palettes/ss8-b12-owned-sunset/vote` was sent with headers `idempotency-key, x-session-token, content-type` and failed with `net::ERR_FAILED`.
  - The console reported *"blocked by CORS policy: Request header field idempotency-key is not allowed by Access-Control-Allow-Headers"*.
  - The UI showed "Failed to publish: No response — the network or the service's TLS certificate failed" in the first u5 attempt (`E/run-b12-inj+u5+vote+sweep.json`), and the availability latch then tripped to "backend offline — saved locally".
- **What this means for the rows below:** U-5 and Meta U-4 decide their **server** leg through a Playwright pass-through route (`passWrites`/`route.fetch`), which bypasses the browser preflight. Same-origin prod is not witnessed.
- **Owner:** consumer (`api/`). **Cure:** add `Idempotency-Key, If-Match` to `Access-Control-Allow-Headers`, and expose `ETag` if the client reads it.
- **Also observed:** the API's colour validator admits malformed `rgb(...)` bodies, including the markup-bearing string above. The owner is consumer (`api/` colour schema).
